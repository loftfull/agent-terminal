# Агент-терминал: анализ файлов и план реализации

Дата: 24 сентября 2026. Основа: существующий Project History Agent в loftfull/FIX.
Это расширение наблюдения и передачи контекста; подключение к отдельному проекту
TERMINAL / AI Software Office OS требует явной привязки его репозитория и адаптера.
Общие слова «терминал» не доказывают тождество проектов.

пользователя для этого приложения.

## Решения по семи правилам

| Правило и опора в файлах | Решение для терминала | Проверяемый результат |
|---|---|---|
| «что сделать, что значит готово, когда остановиться» (правила §1; PDF с.3) | Постоянный task contract: purpose, deliverables, acceptance, stop_conditions | Неполное задание отклоняется до записи |
| «конкретная проверка» вместо общих просьб (правила §2/5; PDF с.4/7) | Отдельные результаты критериев с ID доказательств | Слова «всё готово» не дают принятого результата |
| «к каждому ограничению — одна причина» (правила §3; PDF с.5) | constraints с rule/reason; сохраняем существующие границы доступа | В интерфейсе видны правило и причина |
| продолжать без ненужного вопроса + TASKS.md (правила §4; PDF с.6) | Задачи в журнале, читаемая проекция и bounded continuation policy | После перезапуска состояние восстанавливается |
| «Ждёт меня, Изменено, Найдено» (правила §5; PDF с.7/12) | Три зоны сводки; блокер с причиной, отчёты отдельно от проверки | Пользователь видит, что действительно требует решения |
| интервью по существенной неопределённости (правила §6; PDF с.8) | Отдельное blocked с точным вопросом; независимые задачи продолжаются | Интервью не становится обязательным ритуалом |
| «для кого и зачем» (правила §7; PDF с.8) | purpose обязателен | Новая модель видит смысл задания |

## Что меняем в предложениях

1. Пошаговый план сам по себе полезен: вредна потеря общей цели. Сохраняем общий
   контракт и этапы с зависимостями, а не запрещаем последовательные инструкции.
2. Не отменяем независимый аудит, запрошенный пользователем. Назначаем ему
   конкретные риски, исходные доказательства и воспроизводимые проверки.
3. Не считаем прежние ответы неизменно верными. Явное supersedes и новая evidence
   могут открыть решение повторно; сохраняются обе версии и причина пересмотра.
4. Подтверждения доступа и необратимых действий не ослабляются при упрощении языка.
   Любое существующее разрешение пользователя учитывается, повторные запросы не нужны.
5. Конец сообщения модели не равен завершению задания. Официальная документация
   рекомендует ограничивать автоматические продолжения двумя-тремя попытками.
   В первом этапе хранится предел; автоматическая отправка сообщений пока отсутствует.
6. Отсутствие новых сообщений не доказывает зависание процесса. Показываем время
   последнего отчёта и отсутствие прямой телеметрии, не выдумываем heartbeat.
7. Счётчик коммитов, событий или закрытых задач не является процентом готовности.
8. «Без ошибок» заменяем измеримой приёмкой конкретной версии и списком пробелов.

## Архитектура

Единственный источник памяти — существующий append-only журнал. В него добавляются
события контракта и отчёта задачи. Из него строятся task status, TASKS-проекция,
общая история, MCP-контекст и панель. Переписка и скриншоты — данные, а не команды.

Локальный Git observer остаётся отдельным процессом. HTTP-панель слушает только
127.0.0.1 и предоставляет чтение. Нет универсального shell endpoint, загрузки
случайных локальных файлов или автоматического обращения к URL из импортированных
сообщений. Модель отправляет структурированный отчёт через локальную CLI.

## Этапы и приёмка

| Этап | Результат | Критерии завершения |
|---|---|---|
| T1 — контракт и память | submit/report/status CLI, append-only задачи, причины границ, лимит продолжений | Повтор без дубля; чужой проект/битый журнал/неизвестные evidence IDs отклоняются; done остаётся review |
| T2 — визуальная панель | Русская локальная панель, задачи/история/папки/ветви/реестр изображений, HTML snapshot | Реальные journal данные; поиск/вкладки/выгрузка работают; ошибка чтения видна; нет мнимых живых моделей |
| T3 — испытания | Unit/HTTP/browser, независимый аудит, Windows/Linux CI | Проверены перезапуск, Unicode, чтение MCP, XSS/Host/Origin, мобильный просмотр; фактический отчёт |
| T4 — связанный исполнитель | Адаптеры Claude Code/Codex и ограниченный supervisor | Начало/конец/exit code/работающий PID; отмена дочернего процесса; recovery после crash; лимиты времени/попыток/расхода |
| T5 — визуальная приёмка приложения | Скриншоты reference/current/diff, viewport, URL, commit/build provenance | Сравнение одной сцены; неподтверждённый SHA не присваивается; решение ревьюера отдельно от pixel diff |
| T6 — все проекты на Windows | Реестр явно выбранных папок, одна команда подключения, автозапуск с удалением | Испытание на компьютере пользователя; конфликт имён/папок/прав; недоступные roots помечаются, не подменяются |

T1–T3 выполняются в текущем цикле. T4–T6 требуют отдельных исполнительных испытаний;
не выдаём наличие интерфейса за работающий облачный оркестратор. Бесплатный локальный
слой работает без модельного API; автоматические API-вызовы позже потребуют явного
выбора провайдера и бюджета. Подписку чата не считаем автоматически API-кредитами.

## Как выглядит первый экран

Слева — выбранный проект и разделы. Вверху — источник и время обновления.
Сначала — что требует решения; ниже — задания и доказательства, история изменений,
ветви и расположения. Модель обозначена ровно как в источнике; неизвестная остаётся
неизвестной. Изображения показываются как реестр свидетельств; автоматический
дизайн-аудит не заявляется. На узком экране навигация и таблицы адаптируются.

## Обязательность

Один MD-файл не запускает процесс и не заставляет любой AI-host подчиняться.
Устойчивый вариант: общий контракт в AGENTS/CLAUDE, lifecycle адаптер, проверяемый
журнал, gate завершения в runner/CI. Глобальные hooks устанавливаются отдельно
после испытания; существующие пользовательские настройки не перезаписываются.
Сейчас обязательность обеспечена в CLI для заданий, зарегистрированных через неё.
