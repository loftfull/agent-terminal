# Независимый аудит Agent Terminal — 28 сентября 2026

## Заключение

**Полная эксплуатационная готовность не достигнута.** Есть полезное ядро
доказательной истории, CLI/MCP и интерфейс чтения. Сквозной пользовательский путь
обрывается между просмотром GitHub, импортом, исполнением, приёмкой и новой версией.
Число разделов и успешных unit-тестов не измеряет готовность этого пути.

Полная перепись не обоснована. Сохранить историю, происхождение, изоляцию проектов,
версии и перенос контекста. Исполнение агентов, универсальный чат и телеметрию
подключать через подходящие готовые продукты. До новых возможностей исправить
потерю семантики при дедупликации и неполноту передачи контекста.

## Независимость и покрытие

Три отдельных агента провели read-only проверки backend, пользовательской логики
и аналогов. Основной агент повторил диагностические воспроизведения. Это отдельные
AI-рецензенты текущей среды, **не внешний человек и не A6 другой независимой моделью
по полному исходному архиву**. A6 остаётся открыт.

Проверены исходники baseline, опубликованный HTML-снимок, журнал, свежий doctor,
228 Python-тестов и специальные probes. Реальные аккаунты моделей, установка на
Windows пользователя, непрерывный сбор и текущий браузерный рендер не проверены.
Аналоги изучены по текущим официальным страницам, без установки и сравнительного
benchmark. SHA upstream здесь не закреплены: код не переносился; перед внедрением
обязательны точная ревизия, лицензия и интеграционная приёмка.

## Пробелы архитектуры и риски, отдельно от дефектов

1. **Нет завершения приёмки.** terminal_control.py:110–121 переводит done в review,
   accepted всегда false, accepted_count=0, acceptance_gate=not_implemented.
   Нужна отдельная операция решения проверяющего, связанная с критериями, evidence
   и SHA артефакта, включая отказ и отзыв приёмки. Самоотчёт агента её не заменяет.
2. **Нет write gateway.** HTTP намеренно read-only (POST405). GitHub — public API
   snapshot + localStorage; поправка — экспорт applied:false. Нет проверенного
   импорта этих форматов с project binding, dry-run, receipt и повтором без дубля.
3. **Согласованность записи ограничена.** append_mutation_batch использует lock,
   но не принимает expected_tip/project_id. Устаревший handoff.patch записывается
   после более нового: last-writer-wins, оба события остаются в журнале. Это
   отсутствие optimistic conflict API, а не повреждение байтов. Документ HUB
   ARCHITECTURE в разделе canonical mutation описывает целевой контракт слишком
   утвердительно: expected-tip gateway пока не реализован.
4. **Контекст компилируется тремя путями.** TerminalHub.context, FixConnect.prompt
   и Python L0/L1/L2 расходятся по форме и правилам. Нужен единый контракт и общие
   fixtures/reference closure. search_evidence пагинируется без expected tip;
   это открытая граница согласованности, не воспроизведённая потеря поиска.
5. **Нет реального provider-пути.** Нужны capabilities, разрешённый запуск,
   события, отмена, reconnect, ошибка, результат и проверка. Запись running не
   означает heartbeat. LangGraph/Langfuse сейчас ссылки, не интеграции.
6. **Нет полного visual pipeline.** Снимок сохранённой версии не доказывает вид
   текущего кода. Нужны build SHA, screenshot hash, viewport, время и preview.
7. **Нет доказательства экономии.** Символы разных наборов данных не равны токенам
   и стоимости одинакового задания. Нужны usage конкретного provider, тариф и
   сравнение качества решения при полном/целевом пакете.
8. **Черновик поправки может исчезнуть:** textarea живёт только в DOM, renderContent
   заменяет узлы. Риск по исходникам, без DOM/native воспроизведения. Сохранить
   черновик в state с привязкой к проекту и tip; проверить polling и навигацию.
9. **Эксплуатация не принята:** пользовательский Windows, backup/restore после
   сбоя, архивы и их покрытие, private GitHub auth, browser/mobile/accessibility.
   Валидная hash-chain без внешнего witness не доказывает отсутствие усечения хвоста.

10. **Масштабирование не измерено:** replay проверяет dedupe линейным поиском для
    каждого события, что даёт квадратичный рост работы; polling повторяет полное
    чтение каждые5сек. Нужен benchmark 1k/10k/100k событий перед выбором индекса
    и materialized projection. Текущее неприемлемое время ответа не доказано.

нашего незавершённого хаба в своих исполнении/чатах/поиске/телеметрии.

## Что изменить принципиально

- Единица продукта — проверяемый результат и его история, а не новый реестр.
- Один канонический журнал; внешние системы поставляют наблюдения через gateway.
- Один контракт контекста для UI, MCP и экспорта; бюджет не может молча удалить
  обязательные ограничения, отменённые решения и происхождение.
- Одна машина состояний выполнения и отдельная приёмка результата.
- Один внешний исполнитель в первом пилоте. Не внедрять сразу несколько runtime.
- Интерфейс показывает next action, блокеры и версию; детали и происхождение
  доступны по запросу. Раздел не считается работающим только из-за наличия кнопки.

## Порядок завершения и наблюдаемая приёмка

| Очередь | Работа | Gate |
|---|---|---|
| 1 | D1–D4, доменная валидация и совместимость replay | Разные события не исчезают; ошибочная запись отвергнута; все обязательные ссылки целевого пакета разрешаются; отмена сохраняется UI/MCP. |
| 2 | Gateway + task acceptance | Импорт GitHub и поправки дают receipt; повтор без дублей; неверный проект/старый tip отклонены; критерии позволяют принять/отклонить конкретный результат. |
| 3 | Один внешний executor | Реальная задача даёт события, отменяется, переживает reconnect, различает fail и success; ключи не уходят в браузер/журнал. |
| 4 | Версия и реальный вид | Один SHA связывает diff, проверки, screenshot и preview; restore в новый worktree не откатывает историю. |
| 5 | Передача между двумя hosts | Новый host получает ограничения, отмены, источники и следующий шаг; повтор/переключение проектов не смешивают данные. Недоступный архив отмечен. |
| 6 | Эксплуатационная приёмка | Windows установка/запуск/обновление, browser/mobile/accessibility, backup+restore и измеренный context budget. A6 отдельно. |

Минимальный полноценный сценарий: подключить репозиторий → привязать project_id →
импортировать наблюдение → назначить задачу готовому исполнителю → получить diff
и проверки → принять результат → увидеть версию → продолжить в другом host →
восстановить прошлый код без отката истории. Только этот проход подтверждает
функциональную готовность хаба; проценты готовности сейчас не вычисляются.
